# 告别 KEDA：K8s 1.37 原生 HPA Scale-to-Zero 落地实战，空闲 Worker 直接缩到 0

> [!warning] 版本与字段校验
> 本文按来源文章整理。`HPAScaleToZero`、特性门控参数和 HPA 指标目标语义属于版本相关内容，上线前应以 Kubernetes 1.37 官方文档和目标集群实际行为为准。

队列消费者、定时任务 Worker 这类"忙时爆满、闲时归零"的负载，空闲时还占着副本，纯属烧钱。过去想让它"没活干就缩到 0 副本"，你只能上 KEDA 或 Knative——原生 HPA 死活做不到，因为基于 CPU/内存利用率的 HPA，在副本数为 0 时算不出目标值（分母为 0），官方直接拒绝。Kubernetes 1.37 把 **HPAScaleToZero** 特性门控推进到 Beta，原生 HPA 终于能合法地把 Deployment 缩到 0。本文讲清原理边界、落地配置，以及与 KEDA 的取舍，并附六个生产翻车点。

## 一、为什么"缩到 0"长期以来是个难题

HPA 基于"利用率"扩缩时，目标副本数 = 当前总用量 / 单副本目标用量。当副本数为 0，分子（当前用量）无法用"每副本平均"表达，HPA 控制器无从下手——它不知道"0 个副本时该不该维持在 0"。因此历史上 `minReplicas: 0` 对 Resource 指标是无效的。

解决思路是： **用"与副本数无关"的需求信号来驱动缩容** 。队列深度、待处理消息数、外部传感器的读数，这些指标表达的是"还有多少活要干"，而不是"每个 Pod 用了多少资源"。HPAScaleToZero 正是放开了对这类 External/Object 指标缩到 0 的限制。

## 二、原理讲解：1.37 做了什么

### 2.1 HPAScaleToZero 特性门控（1.37 Beta）

在 1.37 中，当集群开启 `HPAScaleToZero` 特性门控后，HPA 允许 `minReplicas: 0` ，并且当外部/对象指标显示"无需求"时，把副本缩到 0。HPA 控制器在评估缩容目标时，会先判断当前指标值是否已经低于"维持 1 个副本"的阈值；若是，则允许降到 0。

### 2.2 硬性约束

- **只支持 External 与 Object 指标** ，不支持 Resource（CPU/内存）指标。因为 Resource 指标无法在 0 副本时表达需求；
- 指标必须表达"独立于 Pod 数量的需求"，典型如队列深度（ `queue_messages_visible` ）、Kafka lag、待处理任务数。

### 2.3 防抖动：默认 5 分钟稳定窗口

从 0 扩容有冷启动成本，从 N 缩到 0 也不能太敏感（避免任务一来一回反复横跳）。HPA 默认用 `stabilizationWindowSeconds` （默认 300 秒）对缩容决策做平滑，突发流量不会立刻把集群缩没。扩容侧则可设 0 以追求快速响应。

## 三、实战：原生 HPA 缩到 0 的完整配置

### 3.1 集群开启特性门控（1.37 Beta）

```
# 控制面组件开启 HPAScaleToZero（具体 flag 以 1.37 文档为准）
# --feature-gates=HPAScaleToZero=true
```

### 3.2 HPA 定义（队列深度驱动）

```
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: queue-worker
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: queue-worker
  minReplicas: 0          # 关键：允许缩到 0
  maxReplicas: 20
  metrics:
    - type: External
      external:
        metric:
          name: queue_messages_visible
        target:
          type: Value
          value: "0"       # 队列为空即缩到 0
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 300   # 5 分钟防抖
    scaleUp:
      stabilizationWindowSeconds: 0
```

### 3.3 与 KEDA 的对比

KEDA 依然有价值：它自带几十种事件源连接器（Kafka、RabbitMQ、AWS SQS…），并把它们统一成 `ScaledObject` ，省去你自己暴露 External 指标。但"缩到 0"这个核心能力，1.37 之后原生 HPA 也能做。取舍： **如果你已经有 Prometheus 暴露队列深度等 External 指标，直接用原生 HPA 即可；若想省去指标暴露、直接对接各种消息中间件，KEDA 仍更省事。**

### 3.4 冷启动与回弹优化

```
# 配合就绪门控与较快的扩容，缓解从 0 拉起延迟
spec:
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 0
      policies:
        - type: Percent
          value: 500
          periodSeconds: 15
```

## 四、生产环境注意事项

- **冷启动延迟** ：从 0 到 1 需要拉镜像、起进程、建连接，第一笔任务可能超时。对延迟敏感链路，建议 `minReplicas` 留 1，或用"预热副本 + 缩到 0 仅用于非关键链路"。
- **指标必须表达独立需求** ：务必用 External/Object 指标，CPU/内存配 `minReplicas:0` 会被 HPA 拒绝。
- **就绪探针** ：Worker 启动后要先标记 Ready 再接活，避免接到任务却没准备好。
- **指标源可用性** ：缩到 0 依赖外部指标可读；指标源挂了，HPA 可能卡在 0（无活）或猛扩（误读为海量待处理）。给指标源做高可用，并在指标缺失时配置保守的兜底行为。

## 五、踩坑实录：六个真实翻车点

**坑 1：用 CPU 指标配 `minReplicas: 0` ，HPA 直接报错不接受。** 原生只接受 External/Object 指标缩到 0。务必改用队列深度类指标；若团队暂时没有 External 指标管线，先用 KEDA 顶上，不要硬磕原生 HPA。

**坑 2：从 0 扩容冷启动慢，首批任务超时失败。** 没有预热，消息已就绪但 Pod 还在拉镜像。解决：对延迟敏感服务保留 `minReplicas: 1` ，或前置消息重试/死信队列，让慢启动的 Pod 有时间就绪。

**坑 3： `stabilizationWindowSeconds` 太短，副本在 0 和 N 间疯狂抖动。** 突发流量一来一回，造成资源浪费与处理延迟。把缩容稳定窗口设到 300 秒以上，必要时对缩容加 `policies` 限制单步幅度。

**坑 4：指标源故障导致 HPA 行为异常。** 外部指标拉取失败时，HPA 可能沿用上次值或拒绝缩放，导致该缩不缩、该扩不扩。给指标管线加健康检查与兜底，并在 Prometheus/Adapter 层做告警。

**坑 5：缩到 0 后忽略就绪探针，Pod 起来就接活却未初始化完。** Worker 要等 DB/缓存连接建立再 Ready，否则任务失败率飙升。务必配 `readinessProbe` ，并在应用启动时完成依赖预热。

**坑 6：和 KEDA 共存导致双重缩放冲突。** 既装了 KEDA 的 ScaledObject 又配了原生 HPA 指向同一 Deployment，两者打架。二选一，或在迁移期先删其一，待原生 HPA 稳定后再下线 KEDA。

## 六、深度延伸：Scale-to-Zero 的经济学与生产阈值

缩到 0 表面上省的是“空闲副本的账单”，但背后的经济学值得算细。一个常驻 2 副本的 Worker，按中型云厂商价格一年就是一笔不小的固定支出；当它只在每天上午两小时有活时，缩到 0 能砍掉约 80% 的空闲成本。但省钱不是无条件的——冷启动代价要量化：从 0 拉起一个 Pod，包含调度、拉镜像（若节点没有缓存则更慢）、起进程、建连接、预热，链路延迟可能从毫秒级变成秒级甚至十秒级。对“用户点击后异步处理”的队列任务，这十秒可以接受；对“同步请求必须立刻返回”的接口，则不可接受。因此我们给一个简单阈值：延迟敏感、同步、SLA 严苛的负载，保留 `minReplicas: 1` ；异步、批处理、webhook 接收类负载，才放心缩到 0。

哪些负载最适合缩到 0？队列消费者（Kafka/RabbitMQ/SQS worker）、定时批处理 Job 的常驻触发器、CI 构建 Agent、webhook receiver——它们的共同特征是“有活才需要，没活纯烧钱”。哪些不适合？低延迟 API 网关、长连接信令服务、需要预热缓存的推荐服务——它们的冷启动成本超过了空闲成本。这个分类比“技术能不能”更重要，因为 Scale-to-Zero 是经济决策，不是技术炫技。

冷启动优化有几招：第一，镜像预热——用 DaemonSet 或节点池预拉常用镜像，让从 0 扩容时省下拉镜像时间；第二，就绪门控——Worker 必须在 `readinessProbe` 通过后（即依赖已建连）才接活，避免在“半初始化”状态丢任务；第三，调度亲和——把这类弹性 Worker 调度到已经有基础镜像缓存的节点池，缩短拉起时间；第四，若在极端延迟场景，用 `minReplicas: 1` 做“常驻保底 + 峰值扩容”，既控成本又保延迟。

指标侧的工程也不能省。要让 HPA 缩到 0，你得先有一个“表达独立需求”的外部指标。最常见做法是用 Prometheus 采集队列深度（如 `rabbitmq_queue_messages` 、Kafka consumer group lag），经 Prometheus Adapter 暴露成 `external.metrics.k8s.io` 的 `queue_messages_visible` ，HPA 读它即可。这里有个坑：指标名必须与 HPA 里写的 `metric.name` 完全一致，且 Adapter 的 `rules` 配置要把该指标显式暴露，否则 HPA 会一直 `<unknown>` 。最后，迁移节奏上，若你已经在用 KEDA，不必立刻删：可以先在同一集群并行跑原生 HPA 观察一周，确认缩容/扩容行为与 KEDA 一致、冷启动达标后，再下线 KEDA 的 ScaledObject，避免“为了用新特性而让生产断流”。

## 七、落地速查与从 KEDA 迁移清单

把前面要点收敛成可执行的清单，并给出从 KEDA 平滑迁移的节奏。

落地前确认三件事：

1. 集群已开 `HPAScaleToZero` 特性门控（1.37 Beta），且 HPA 用的是 `autoscaling/v2` ；
2. 你的指标是 External/Object 类型（队列深度、Kafka lag、待处理任务数），不是 CPU/内存；
3. Prometheus Adapter 已把该指标稳定暴露成 `external.metrics.k8s.io` ，且指标名与 HPA 里 `metric.name` 完全一致。

上线配置三要素：

- `minReplicas: 0` 开启缩零；
- `behavior.scaleDown.stabilizationWindowSeconds` 设 300 秒以上防抖；
- `behavior.scaleUp` 可设 `stabilizationWindowSeconds: 0` + `Percent 500/15s` 追求快速回弹。

从 KEDA 迁移的节奏（避免断流）：

- 阶段一：同一集群并行跑原生 HPA 与 KEDA 的 ScaledObject，但指向 **不同** Deployment（或先让原生 HPA 指向副本 0 的影子 Deployment）观察一周；
- 阶段二：确认原生 HPA 的缩容/扩容行为、冷启动延迟与 KEDA 一致后，把业务流量切到原生 HPA 管理的 Deployment；
- 阶段三：确认稳定，再删除 KEDA 的 ScaledObject 并下线 KEDA controller。

迁移期最忌"两套同时管一个 Deployment"——双重缩放冲突会让副本数在 0 和 N 间乱跳。务必二选一，或错开管理对象。

最后给一个经济决策口诀：同步、低延迟、SLA 严苛 → 保留 `minReplicas: 1` ；异步、批处理、webhook 接收 → 放心缩到 0。先按这个口诀分类负载，再决定哪些值得缩零，别为了"新特性"把延迟敏感的接口也缩没了。

## 八、总结

1.37 的 HPAScaleToZero 把“空闲缩到 0”从“必须上 KEDA”变成了“原生可选”。记住铁律： **缩到 0 只认 External/Object 指标，不认 CPU/内存；冷启动要兜底，防抖要够长** 。对队列类 Worker，这是立省成本的一行配置，但上线前务必把“从 0 拉起”的延迟链路测透：用“延迟敏感保留 1 副本、异步负载才缩到 0”的阈值做经济决策，配镜像预热与就绪门控压低冷启动，并用 Prometheus Adapter 把队列深度稳定暴露成外部指标，别让省钱变成超时。

## 九、监控与消息可靠性补充

开启 Scale-to-Zero 后，副本数频繁变为 0 可能使传统 Pod 数量告警误报。建议把“期望副本数为 0 且指标源健康”视为正常态，只对指标源不可达、无法决策，或长时间卡在 0 但队列仍有积压这两类情况告警。

对于消息中间件场景，给消费者增加重试和死信队列，可以吸收冷启动期间的延迟抖动；同时要持续监控伸缩行为是否与队列指标一致。

module.openfga_lifecycle_monitors.local.service_notifications

The Revolution DORA webhook mention is derived as format("@webhook-revolution_dora_incident-%s", s.team) with s.team = "permanents-1" (set in openfga_monitors.tf), producing "@webhook-revolution_dora_incident-permanents-1". Live Datadog data (queried via MCP) shows every existing monitor for this same team uses the integration name "@webhook-revolution_dora_incident-permanents1" (no hyphen) — e.g. monitor IDs 101296693, 31297907, 23686335, 90130990 all reference "webhook-revolution_dora_incident-permanents1". lightning-core's own monitoring/main.tf confirms this explicitly: the permanents-1 team block sets team = "permanents-1" but hardcodes revolution_webhook = "@webhook-revolution_dora_incident-permanents1" as a literal override rather than deriving it from `team`, because the two values differ for this specific team. This module derives the webhook name purely from `team` via string formatting, so for prod alerts on this new monitor the DORA webhook mention will reference a non-existent integration and silently fail to route, while Opsgenie and the Teams channel mentions (which use explicit prod_channel/opsgenie fields, not derived from `team`) will still work correctly. infrastructure/platform/common/openfga_lifecycle_monitors/main.tf:79
Fix: Add an explicit `revolution` (or `dora_webhook`) field to the openfga_settings object type, and set it to "@webhook-revolution_dora_incident-permanents1" for configuration-storage instead of deriving it from `team` — mirroring how prod_channel/non_prod_channel/opsgenie are already explicit fields rather than derived strings. Verify the correct webhook name with the team that owns the Revolution DORA integration before merging, since this only affects the prod tier's alert messages and is not caught by `terraform validate`.

priority2_message.tftpl

Vendored template diverges from the lightning-core original: the recovery branch now re-posts to `${channel}` (the original only sent `opsgenie_close` on recovery, with no channel re-notification), and the alert branch newly renders `${revolution}` (the original computed a `revolution` local but never passed or rendered it in any template). These look like deliberate adaptations rather than accidental drift, but are worth a maintainer's explicit sign-off since they change notification volume/behavior versus the module this was vendored from. infrastructure/platform/common/openfga_lifecycle_monitors/priority2_message.tftpl:8
Fix: Confirm with the module owner/reviewer that (a) recovery messages should now also post to the team channel, and (b) whether the Revolution DORA integration needs an explicit 'close' mention on recovery (similar to opsgenie_close) to resolve the incident, or if it auto-resolves from the monitor's recovery webhook payload.
